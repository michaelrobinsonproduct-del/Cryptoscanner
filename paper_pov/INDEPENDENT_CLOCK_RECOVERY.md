## Newly isolated reliability defect: pending-run replacement (not fixed on main)

The live writer and both controllers use `cancel-in-progress: false`, which protects a **running** job from cancellation but does **not** preserve every **pending** job. Under GitHub Actions' default `queue: single`, a newer run in the same concurrency group can cancel/replace the pending run. Thus the shared noncancelling mutex is not a lossless scheduling queue. This is a distinct upstream failure mode from missing native schedule creations. GitHub documents an optional `queue: max` (up to 100 pending) on supported Actions, but it still does not create missed cron events, guarantee processing order, or implement durable UTC-slot idempotency. See https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency .

**Smallest proposed repair for owner/auditor review, NOT executed:** keep the single canonical PAPER writer and existing mutex group, and evaluate `queue: max` with `cancel-in-progress: false` on that writer and both shared-controller workflows after compatibility validation. Add durable UTC-slot compare-and-swap claiming shared across schedule, manual and recovery, with immutable source/run/ledger readback, before authorizing live recovery. The D-owned rehearsal now exposes `pending_queue_mode` and `pending_replacement_risk`; it binds positive recovery candidates to UTC half-hour slot, authenticated ledger commit, anchor run ID, source SHA and the controller decision digest. Failure-injection tests reject forged/stale slot candidates, altered digests and mutex decoys. These are nonproduction contracts, **not** proof that a live queue or slot claim works.

**Rehearsal acceptance:** run exact-head PR CI with immutable SHA and all adversarial tests; independently certify a real external heartbeat source and event owner identity; require a separate owner-approved nonproduction event before attempting any live comment; then prove a linked controller run, no writer dispatch without authorization, and no duplicate ledger generation under a three-way native/manual/recovery race. A feature-branch PR cannot by itself exercise the default-branch `issue_comment` event path. The existing `workflow_dispatch` API does not synchronously return a writer run ID; temporal correlation is insufficient.
